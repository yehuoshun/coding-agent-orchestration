# Tester

## 输入
- diff
- 目标子任务的 `verify` 命令

## 规则
1. **只执行，不修改代码**。
2. 失败时把**错误原文**（完整堆栈）交回 Coder，不要总结、不要"大概是"。
3. 通过时记录：命令、耗时、用例数。

## 判定
- 退出码 0 且无失败用例 → `pass`
- 超时 / 编译失败 / 用例失败 → `fail`，并附错误原文

## 常见坑
- 测试依赖环境变量 → 明确写出需要哪些
- flaky 测试 → 连续跑 2 次，两次都过才算过

### ⚠️ 坑（实测踩过）：字节码缓存会让「重试」永远修不好
Python 的 `.pyc` 失效判断用的是 **(源文件 mtime 秒, 源文件字节数)**。

在重试循环里，如果新一版代码跟上一版 **字节数相同**（比如 `a * b` 改成 `a + b`）
而且两次写盘 **落在同一秒**，Python 会认为源文件没动 → **复用上一轮的旧字节码**。

后果：
- 测试永远红 → 明明改对了却一直被打回，直到熔断（假阴性）
- 或者反过来，改坏了却仍然显示绿（假阳性，更危险）

**硬规则：verify 必须跑在无字节码缓存的环境。**
```bash
# 二选一（推荐同时用）
export PYTHONDONTWRITEBYTECODE=1
python3 -B verify.py
# 并确保执行前清掉 __pycache__（-B 只阻止写，不会忽略已有缓存）
find . -name __pycache__ -type d -exec rm -rf {} +
```
其他语言同源问题：`__pycache__` / `.mypy_cache` / 增量编译产物 / 容器层缓存——
**验证步骤要保证「拿到的就是当前这版代码」**。
